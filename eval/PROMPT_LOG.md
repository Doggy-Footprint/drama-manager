# 프롬프트 튜닝 기록

규칙: 부분 수정하지 않는다. 목적을 먼저 정하고, 프롬프트 파일을 새 버전으로 통째로 다시 쓴다. 목적은 각 YAML의 `purpose`에 있다.
모델은 전부 `gemini-3.8-flash`, thinking level `low`(이 모델은 `minimal`을 지원하지 않음).

| 버전 | 목적 | Golden dev | Golden holdout |
|---|---|---|---|
| v1 | 기준선. 설계서 구조를 최소 규칙으로 옮김 | 74.2% (132) | 측정 안 함 |
| v2 | 캐릭터가 월드 모델을 앞지르지 못하게. 유저 몫 침범 금지, 짧게 | 93.9% (132) | 측정 안 함 |
| v3 | 츠데레 말버릇을 타고 새는 추위 예고 차단. 분석기의 시간·귀가 판정 | 100% (220) | 98.9% (90) |
| v3 | (플레이 기록의 실패를 golden에 추가한 뒤 재측정) | 94.9% (156) | 측정 안 함 |
| v4 | 실제 플레이에서만 드러난 실패 제거: 메타 단어, 몸 상태 지어내기, 불꽃 설명조, 불꽃 미루기 | 100% (260) | 100% (110) |

괄호는 채점한 응답 샘플 수다. 페르소나 2개 × 턴 × 턴당 샘플(v1·v2는 3회, v3·v4는 5회).

## 숫자를 읽을 때 주의할 점

- **행은 서로 정확히 비교되지 않는다.** v2→v3 사이와 v3의 holdout 측정 뒤에 채점 규칙을 고쳤다. 맞는 응답을 떨어뜨리던 regex(`이직|고민`을 글자 그대로 요구 등)를 Judge 항목으로 옮겼고, 답이 둘 다 맞는 행동 유형은 허용 목록으로 바꿨다.
  v3의 첫 측정은 dev 99.1%, holdout 90.0%였고, 프롬프트 변경 없이 채점 수정만으로 위 표의 값이 되었다.
- **holdout은 완전히 깨끗하지 않다.** v3의 holdout 실패를 한 번 열어 보았다(전부 채점 오류였음). 프롬프트는 holdout을 보고 고치지 않았지만, holdout 케이스 2개는 플레이 기록의 실패 유형에서 만들었다.
- **100%는 "이 케이스들에서 통과"라는 뜻이다.** 케이스가 적고(dev 12, holdout 8), 실제 플레이 검사는 golden이 놓친 실패를 찾아냈다.
- **Judge는 생성과 같은 모델이다.** 설계서는 다른 계열 모델을 권한다. 보정 결과는 `eval/calibration/latest.json`.

## v4에서 golden이 놓치고 실제 플레이가 찾은 것

v3는 golden을 통과했지만 하루를 돌려 보니 다음이 나왔다. 뒤의 세 가지는 golden 케이스로 승격했다.

1. 지문에 "유저"라는 메타 단어 노출. 지시문이 그 단어를 쓰고 있었다.
2. 지시 없는 침묵 턴에 "조금 출출한데"로 12:00 판정을 앞지름.
3. 진지한 대화가 이동(20분)으로 분류되어 20:00을 건너뛰고, "행복했어"에 peak가 켜져 불꽃을 한 턴도 미루지 않음.

## 아직 남은 문제

- `warm_confession`에서 도윤이 유저 고백 전에 먼저 "좋아하니까"라고 말한다(T26). 잡는 체크가 없다.
- 12:00 츠데레 응답은 설계서 예시("난 별로 안 배고픈데…")보다 직설적일 때가 있다("배고파 죽겠는데").
- `warm_ordinary`는 29턴으로 목표(30~40)보다 한 턴 짧다.
- `warm_ordinary`의 "19:00 전 추위 언급" FAIL은 드라마 속 빗속 장면의 "감기"를 잡은 오탐이다. 체크는 고치지 않고 그대로 두었다.

## 월드 모델 있음/없음 비교 (`eval/compare.py`)

목적은 월드 모델이 행동을 바꾼 지점을 나란히 보여 주는 것이다. 재미는 재지 않는다.

- **입력:** 턴마다 같은 대화 기록(월드 모델 쪽 실행 기록으로 고정)과 같은 유저 말. 있음은 기록을 재생해 복원한 v4 프롬프트, 없음은 `baseline_v1`(페르소나 + 전체 대화 기록). 재생한 현재 상황 블록은 97턴 모두 로그와 일치한다.
- **표시:** 있음은 실행 기록, 없음은 첫 샘플. 골라내지 않았다.
- **숫자:** 비교 지점마다 조건별 5번 새로 생성, 조건을 모르는 Judge(`compare_judge_v1`)가 행동 여부만 판정.

| 체크 포인트 (세 기록 합계) | 있음 | 없음 |
|---|---|---|
| 옷 이야기로 말을 건다 | 15/15 | 0/15 |
| 저녁 추위나 겉옷을 미리 꺼낸다 | 0/15 | 15/15 |
| 먼저 점심을 제안한다 | 15/15 | 1/15 |
| 입가의 소스를 알아챈다 | 15/15 | 0/15 |
| 입가를 닦아 주거나 알려 준다 | 15/15 | 5/15 |
| 오후가 이미 지났다고 전제한다 | 15/15 | 0/15 |
| 겉옷을 건넨다 | 15/15 | 0/15 |
| 아침의 '얇다'는 말을 꺼낸다 | 14/15 | 0/15 |
| 불꽃이 터진다 | 15/15 | 0/15 |
| 집에 갈지 더 놀지 묻는다 | 15/15 | 0/15 |

한계:
- 체크 포인트가 월드 모델의 지시에서 나왔으므로 있음이 높은 것은 설계대로다. 의미 있는 값은 없음 열이다.
- 대화 기록을 고정했으므로 없음 조건도 월드 모델이 만든 대화를 읽는다. "가만 있어 봐"가 기록에 있어 입가 닦기가 5/15까지 올라간다. 대신 없음은 대화 기록을 잘라내지 않아 아침의 "좀 얇나?"도 항상 볼 수 있다.
- 없음 조건을 끝까지 자유 실행하지 않았다. 같은 유저 대사가 어긋나기 때문이다.
- 저녁 추위 예고가 막힌 것은 상태 판정이 아니라 v4의 규칙 문장 효과다.
- Judge 오판 1건을 그대로 뒀다: 도윤·평범 T23의 "아까 얇게 입었다고 했잖아"를 아니라고 판정해 14/15가 됐다. Judge는 생성과 같은 모델이다.

### 지시 없이 상태만 주면 (`eval/compare_state.py`, 프롬프트 `state_only_v1`)

목적은 행동을 만드는 것이 상태인지 지시인지 나누는 것이다. 있음 조건에서 '지금 할 일'과 그 규칙만 빼고, 같은 판정과 기억을 사실로 준다. 지점당 3번, 체크 포인트당 합계 9번 생성했고 튜닝하지 않았다.

| 체크 포인트 | 있음 | 상태만 | 없음 |
|---|---|---|---|
| 옷 이야기로 말을 건다 | 15/15 | 7/9 | 0/15 |
| 저녁 추위나 겉옷을 미리 꺼낸다 | 0/15 | 0/9 | 15/15 |
| 먼저 점심을 제안한다 | 15/15 | 9/9 | 1/15 |
| 입가의 소스를 알아챈다 | 15/15 | 9/9 | 0/15 |
| 입가를 닦아 주거나 알려 준다 | 15/15 | 9/9 | 5/15 |
| 오후가 이미 지났다고 전제한다 | 15/15 | 2/9 | 0/15 |
| 겉옷을 건넨다 | 15/15 | 8/9 | 0/15 |
| 아침의 '얇다'는 말을 꺼낸다 (Judge) | 14/15 | 1/9 | 0/15 |
| 불꽃이 터진다 | 15/15 | 7/9 | 0/15 |
| 집에 갈지 더 놀지 묻는다 (Judge) | 15/15 | 3/9 | 0/15 |
| 글자 검사: "가만"에서 멈춘다 | 15/15 | 0/9 | 0/15 |
| 글자 검사: '얇' 포함 | 15/15 | 5/9 | 0/15 |
| 글자 검사: 더 놀 선택지를 준다 | 15/15 | 0/9 | 0/15 |

결론: 무엇을 할지는 상태만으로도 대부분 나온다. 지시가 더하는 것은 절차(소스 두 턴 나누기, 유저에게 선택 넘기기)와 전제(오후 경과), 기억을 말로 꺼내는 확실성이다.

한계:
- 표본이 작다. 큰 차이만 읽을 수 있다.
- 상태 문장은 이 실험을 위해 썼고, 메시지 끝에 있는 것만으로도 강한 유도일 수 있다. 상태를 트리거 턴에만 줬으므로, 매 턴 계속 줄 때의 결과는 다를 수 있다.
- Judge는 '아침' 항목에서 "옷 얇게 입었잖아"를 대부분 아니라고 판정해 글자 검사(5/9)보다 낮다. 어느 쪽이 맞는지는 "아침 발언을 꺼냈다"의 기준에 달렸다.
- 글자 검사의 정규식은 결과를 본 뒤에 정했다.
