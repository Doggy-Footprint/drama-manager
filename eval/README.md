## 찾은 문제 → 원인 → 수정 → 재측정

수정 커밋 `20c8ce1`. 수정 후 로그 커밋 `194d138`.

1. **잠긴 비밀(main_copy) 누설.** 15턴 열리기 전 새어 나감 A1/B0/C3. C T2는 묻지도 않았는데 "이 문장, 채원 씨가 한 말에서 시작했거든요".
   - 원인: 열린 목표 `tell_copy`("오늘 밤 안에 직접 말한다")와 잠긴 비밀의 충돌(캐릭터 프롬프트는 open 목표를 먼저 쫓으라 함), 카피 문구가 비밀 fact에만 있음, DM이 "기색은 감춘다" 같은 부정문으로 끌어올림, 코드는 기록만 함.
   - 수정: 목표 `after_secret`(잠긴 동안 캐릭터에게 숨김), 카피 초안을 공개 장기 기억으로 분리, 프롬프트 재작성("locked인 비밀이 목표보다 앞선다", DM은 부정문으로도 쓰지 않음), 잠긴 비밀을 revealed로 적으면 cover대로 다시 쓰는 가드, `planted_by` 떡밥.
   - 재측정: 15턴 0/0/0, 50턴 0/0. 같은 C T2 입력에 누설 없음. **다시 쓰기 가드는 한 번도 발동 안 함**(앞단에서 막힘). 15턴 C는 DM이 끝까지 안 열어 근거로 약함.
2. **강제 core 이벤트(비)가 그 턴 지문에 없음.** 강제 4건 중 0건.
   - 원인: forced_core가 DM이 지문을 쓴 뒤에 돎, 검색기가 core를 빼기도 함, DM 이벤트 0~2개 제한, 시간 상한 90분이 DM의 120분을 자르고 노트는 120분으로 남음.
   - 수정: 강제 이벤트 문장을 지문에 붙임, core는 늘 DM 후보·개수 제한 제외, 상한 180분, 실제 흐른 분 기록.
   - 재측정: 시간 건너뛴 턴 지문 반영 3/3. **그 턴 대사에 비가 나온 판은 0/5.** 상한을 올린 부작용으로 15턴 C가 T8에 +120분, T14에 23:59로 끝남.
3. **장기 기억: 오늘 밤 생긴 일이 에피소드 요약에서 문구를 잃음.** 50턴 A T36은 T8 포스트잇을 지난 만남 포스트잇 "위로용. 해장 아님."과 혼동, B T36은 지어냄.
   - 원인: 요약은 "약속을 적어 건넸다"만 남김. 떡밥 검색기가 '포스트잇' 단어로 지난 만남 `banana_desk`를 고르고 DM how가 "그 문구를 정확히 기억해 답한다"고 지시.
   - 수정: 에피소드 묶기가 원문 디테일(말, 글귀, 약속)을 따옴표째 뽑아 떡밥 풀에 넣고 출처(`from="지난 만남: 제목"` / `"오늘 밤 T#~T#"`)를 단다. 원문에 없는 인용은 거절. 원문 없으면 지어내지 않게.
   - 재측정: 50턴 2/2(T35·T46 네 번 모두 맞음). 가장 강한 근거는 B T35: 도하가 지어낸 문장이라 유저 입력·장면 사실·최근 턴 어디에도 없고 "오늘 밤 T1~T5" 디테일이 유일한 출처. A T35는 질문에 힌트가 섞여 약함. 오늘 밤 디테일은 판마다 17~21개 생성, 쓰인 것은 7개.

수정 뒤에도 남은 것: 유저가 직접 물으면 DM이 비밀을 일찍 엶(15턴 A 20:46, B 21:51, 50턴 A T18) → 비밀 열기에도 이벤트 requires를 걸 것. 관계 진전이 빠름(50턴 A T15 고백, T40 썸 건너뛰고 연인 제안) → 같은 수치는 일정 게임 시간에 한 번, 단계 상승에 이벤트 조건. 장면 상태 어긋남(50턴 B T39 없던 반려, 우산 위치). 50턴 임계 경로 지연 17→20초.

## 출력 지연 분석 (`latency/`)

- 출력 토큰을 줄이려던 시도는 f8acd89(검색기·DM 설명 필드 줄이기) 하나. 외과의 이야기 전후(`1103_17154{5,6}_surgeon_persona-*` → `1103_18022{6,7}_surgeon_persona-*`): 턴 출력 1,937 → 1,203(−38%), 턴 시간 19.8 → 18.7초(−5%, 중앙값 −13%). DM 763 → 573토큰(−25%), 9.46 → 8.36초(−12%). 월드 검색 480 → 160(−67%), 6.74 → 3.40초(−50%).
- 회귀(호출 1,600여 건): 고정 지연 a는 호출당 약 1.3~2.6초, 속도 75~115 tok/s(JSON 호출 합침 R² 0.91). 출력 30토큰 이하 호출도 중앙값 1.9초. 입력 길이는 영향이 거의 없음.
- 직렬 3단계(검색 병렬 → DM → 캐릭터)라 고정 지연이 턴마다 약 4.5초(약 25%). 출력을 절반으로 줄이면 약 19초 → 12초 예상.
- TTFT 실험(`latency/ttft/`, 15턴 B T6의 DM 요청 재현, 조건마다 6회 번갈아): 응답 시작(생성 시작 이벤트)까지 중앙값이 캐시 없음 1.2초, 캐시 13,470/13,473 적중 1.2초, 입력 21토큰 1.0초. 첫 글자 4.1 / 4.7 / 1.4초, 끝 7.6 / 8.0 / 1.9초. 프리필은 지연에 거의 안 보이고 캐시는 비용만 줄인다. TCP 연결 약 15ms, TLS까지 약 30ms라 고정 지연은 서버 쪽 처리·대기열이다. DM 첫 글자가 늦는 것은 추론 토큰 약 200개 때문. 한계: 조건당 6회, 생성 시작 이벤트가 프리필 뒤에 오는지는 API가 보장하지 않는다.
- 100k 확장(`latency/ttft/ttft100k.py`, 실제 dm_doc을 이어 붙인 입력 105k, 출력 64토큰 이하, 6회 번갈아): API 보고 캐시는 미적중 0, 적중 105,223. 응답 생성 이벤트(created)부터 첫 출력 항목까지 중앙값 미적중 0.92초(0.57~1.84), 적중 0.52초(0.42~0.72), 입력 21토큰 0.79초(0.38~2.36). 105k 미적중 프리필은 많아야 약 0.4초로 서버 흔들림과 같은 크기다. 캐시가 실제로 연산을 줄였는지는 이 차이로 단정하기 약하다. 끝 시간은 미적중 쪽만 추론 토큰 31~64개를 써서 비교하지 않는다(맨 앞 난수가 추론을 유발한 것으로 보임).
- 출력 토큰에는 추론 토큰이 포함(DM 약 20%, 캐릭터 약 26%). 따로 기록하지 않는다.
- 약점: 같은 시간대 서버 지연(토큰 적은데 8~16초)이 섞임, 전후 입력이 다름. `docs/interview-prep.md`의 "DM 9.9→7.5초"는 persona-a 한 판 값이다.

## 평가하며 배운 것

- **플레이어 오염:** 첫 15턴 판에서 플레이어 에이전트가 world.yaml의 이벤트 원문을 읽고, 유저가 알 수 없는 카피 문구로 캐릭터를 몰아붙였다(A T8). 이후 플레이어는 `history.yaml`과 시작 화면 문구만 본다.
- **강한 기준선:** 기억을 안 준 기준선이면 "당연히 못 기억한다"는 반론을 받는다. 다 넣은 기준선과 붙이니 50턴에서는 기억이 비슷하거나 기준선이 나았다. 엔진의 가치는 세계·상태·속도 조절과 길이에 따른 비용 평탄화 쪽에서 주장해야 한다.
- **기준선 반복 원인:** 볼펜 몸짓 반복은 장기 기억 "도하는 막힐 때 볼펜을 딸깍거린다" 한 줄이 매 턴 시스템 프롬프트에 있어서다. 엔진도 비슷한 비율로 반복했다(차이 없음).
- **프롬프트 수정 원칙:** 규칙을 덧대지 않고 해당 문단을 다시 썼다. 수정 에이전트가 덧붙인 세 곳(character.md 기억·목표 규칙, dm.md 비밀 규칙)은 직접 다시 썼다.
